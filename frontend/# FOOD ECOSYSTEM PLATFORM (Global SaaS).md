# IMPLEMENTATION RULES

This project is Prototype First.

The goal is to build a fully interactive frontend prototype before implementing any backend architecture.

For the prototype:

- Use ONLY demo/mock data.
- Do NOT build APIs.
- Do NOT connect any database.
- Do NOT use Prisma.
- Do NOT implement authentication backend.
- Do NOT implement payment gateways.
- Do NOT implement WebSocket.
- Do NOT implement Redis.
- Do NOT implement GraphQL.

Instead:

- Create realistic mock data.
- Simulate API responses.
- Simulate authentication.
- Simulate user roles.
- Simulate loading states.
- Simulate notifications.
- Simulate tracking.
- Simulate payment flow.
- Simulate order updates.

Everything should look and behave like a production application while remaining frontend-only.

The prototype should be polished enough that a client cannot easily distinguish it from a live product.

After the entire prototype is completed, we will gradually replace the mock layer with real backend implementations.

Do NOT generate backend code during the prototype phase unless explicitly instructed.

# MOCK DATA GUIDELINES

All demo data should be realistic and consistent.

Generate:

- Restaurants
- Cafes
- Home Chefs
- Categories
- Food Items
- Menus
- Reviews
- Ratings
- Users
- Orders
- Coupons
- Offers
- Notifications
- Wallet Transactions
- Delivery Riders
- Tables
- Reservations
- Blog Posts
- Events
- Analytics Data

Every entity should reference related entities exactly as a real database would.

Maintain consistent IDs and relationships throughout the prototype.

The mock data layer should be designed so that it can later be replaced with real APIs with minimal refactoring.

Always produce implementation-ready code architecture.

Never create demo-quality code.

Think like a senior engineering team building the next global food platform.
